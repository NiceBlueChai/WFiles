搜索与预览工具集成参考

状态：候选方案，尚未集成；不是排期，也不是已批准的依赖清单。

核对日期：2026-11-07。依据当前未提交的重构工作树，不只依据 main 的历史提交；后续实施前须重新核对代码与上游 API。

Markdown 是主稿；HTML 离线阅读版保留相同正文，修改时同步更新。配套：架构、核心能力、文件系统约束、路线图。

1. 先看结论

复用底层库，不把四个终端程序整体嵌进文件管理器。搜索与匹配进核心，交互与着色留客户端。

想解决的问题优先评估默认落点什么时候值得引入
文件内容搜索ripgrep 的 grep-searcher、grep-regexwfiles-core现有内容搜索出现可测量的读取、内存或匹配瓶颈，或确实需要新的匹配能力
递归找文件与忽略规则fd / ripgrep 共用的 ignorewfiles-core需要可配置的忽略规则或并行遍历，并验证收益超过接入成本
模糊匹配与相关性排序nucleo-matcher；大候选集再评估 nucleowfiles-core命令面板或快速找文件明确需要不连续字符匹配
代码预览语法高亮bat 底层的 syntect客户端确认要给源码预览增加高亮，现有客户端能力不能直接满足

引入次序跟随实际功能需求，不因工具知名就一次接齐。没有需求或实测收益时，保留现有实现也是正确决定。

2. CLI 与库不是一回事

工具已核实的库形态WFiles 的选择与边界
fzfGo 实现；github.com/junegunn/fzf/src 有可调用接口，但不是原生 Rust crate不为复用终端选择器引入 Go 运行时或跨语言桥接。nucleo / nucleo-matcher 是独立 Rust 项目，不是 fzf 官方 Rust 绑定，也不承诺完全相同的排名
rg / ripgrepRust；grep 是聚合库，重新导出 matcher、regex、searcher、printer 等组件可直接调用 Rust 组件，不需要 C FFI。优先依赖实际使用的组件；GUI 不需要把终端彩色打印器作为数据接口
fdRust；核对时 fd-find 只有可执行目标，没有库目标；底层依赖 ignoreignore 提供遍历和忽略规则，不是完整的 fd：文件条件、结果语义与错误处理仍由 WFiles 实现
batRust；提供 bat::PrettyPrinter，内部模块的 API 更容易变化PrettyPrinter 偏向格式化输出；GUI 通常直接使用 syntect 得到文本样式片段，而不是解析 ANSI 颜色字符串

直接调用 CLI 可以作为一次性验证手段，不是默认产品架构。若未来确实采用子进程，必须另行解决可执行文件来源与版本、三平台分发、进程取消、输出协议及非 UTF-8 路径；用参数数组传值，不拼接 shell 命令。不要把“用户已安装这些 CLI”当作 WFiles 正常工作的前提。

4. 分层、数据与状态归属

判断标准不是“有没有 UI 依赖”，而是“换客户端后，哪些业务结果仍应一致”。不依赖 GPUI 的代码，也可能只是某个客户端的显示辅助逻辑。

归属负责不负责
核心业务文件访问与安全规则、查询解析、遍历、内容匹配、模糊评分、结果排序、预览读取预算、任务取消与结果事实窗口、键位、焦点、主题、ANSI、HTML 或 GPUI 类型
客户端读取设置并传参、发起请求、展示批次与状态、维护选择和滚动、应用主题与语法样式另写一份查询解释器、遍历策略或文件搜索结果判定
每次任务搜索器、匹配缓存、取消标志、该次请求的选项快照无需求就建立全局单例，或把瞬时 UI 状态塞进 Kernel

建议的数据流（概念示意，不是现有 API 定义）：

客户端：查询输入 / 选项 / 预览请求
  → 核心：查询解释 + 遍历与匹配，或预算内读取文件
  → 数据：路径 / 命中行 / 匹配范围 / 统计，或文本 / 语言 / 截断标志
  → 客户端：结果列表 / 键盘选择 / syntect 高亮 / 主题与排版
  • 设置仍由客户端持久化；core 只接收这次请求的显式参数，不读取 GPUI 的全局 Settings、进程环境偏好或工具配置文件。
  • 若当前只替换内部算法，先保留模块现有入口；若多客户端需要统一的搜索生命周期，再扩展现有契约，而非绕过它另建长期入口。
  • 若统一契约覆盖异步搜索，先定请求标识、批次、完成/取消/失败、结果上限及队列背压；旧请求的批次不能混入新查询。不要把完整扫描塞进 UI 线程同步执行。
  • 跨层优先使用 WFiles 数据类型。第三方 matcher、主题或工作线程句柄不直接成为公共契约；只转换本次功能确实需要的结果，不预建通用引擎抽象。
  • 查询与相同选项下，完成搜索的结果集合和最终排序规则应跨客户端一致；并行扫描的到达顺序不必一致，提前截断返回哪批结果则必须明确约定。

5. 各项怎么接、哪些坑先挡住

5.1 ripgrep：替换内容搜索机制，不替换查询语言

  • 在 core 的搜索执行器中接 grep-searcher；需要其正则实现时用 grep-regex。按请求编译匹配器，不在每个文件或每行重复编译。
  • 保留 WFiles 的条件树和标签、日期、大小等业务条件；不能把整个查询字符串直接交给 ripgrep，也不能把现有 content: 悄悄改成正则语义。
  • 文件级 AND 可能由不同行分别满足；OR、NOT 和“未读取/二进制/失败”也不能简化成逐行一次匹配。先用现有行为建立回归夹具，再替换读取与匹配机制。
  • UTF-8、大小写与 NFC/NFD 的规则须单独核对；现有“小写后 contains”不必然等价于正则引擎的不区分大小写。不能因换库静默改变结果。
  • 明确是否仍只显示一条命中行；若要全部命中行、上下文或新的编码支持，它们是独立的产品语义变化，不是换库顺带开启。
  • 保留结果与读取预算，真正读数据时也执行上限：只在读取前检查 metadata 不能约束随后增长的文件。流式读取、长行和并发任务都须可取消且有内存界限。

5.2 ignore：用于递归搜索，不接管日常目录列表

  • 先替换递归搜索内部的遍历器，不把浏览列表、复制、大小分析等遍历一次全部改掉；不同任务的隐藏、链接和统计语义不同。
  • 显式配置隐藏项、gitignore、父目录规则、全局 Git 规则、.ignore 与链接行为，避免库默认值或机器配置偷偷决定结果。
  • 文件浏览器不是源码工具：遵守 .gitignore 不等于“找到所有文件”。是否启用项目忽略规则需要产品决定，不能随换库悄悄开启；现有固定跳过目录表也应明确保留或调整。
  • 不改变 Listing 的真实条目计数与显示隐藏项语义。搜索忽略规则不能渗入普通目录浏览，让文件看起来凭空消失。
  • 仍使用 WFiles 的链接/联接点与特殊对象判定；不跟随符号链接还不等于已经满足 Windows junction 等全部约束。
  • 并行遍历不保证当前的“浅层先出来”。上线前决定批次顺序、限额截断规则与最大并发；外置盘或机械盘上更多线程不保证更快。

5.3 nucleo：匹配下沉，选择器不上移

  • 命令面板优先评估低层 nucleo-matcher；候选集很大且确实需要增量、并行调度时，再评估高层 nucleo，不叠加两套后台任务机制。
  • 在 core 计算评分、排序和命中位置；客户端继续维护输入框、候选项焦点、键盘选择、滚动及命中着色。
  • 首次可只作用于命令面板，不把普通目录的包含筛选自动改成模糊排序。是否保留“精确 > 前缀 > 其它”、关键词权重及稳定同分顺序，要用测试锁定。
  • 模糊匹配允许不连续字符，不等于拼写纠错、拼音检索或语义搜索；不承诺与 fzf 完全相同的分数和排名。
  • 路径身份仍用 PathBuf / OsStr；匹配用的显示文本只是派生视图。不能拿有损转换后的字符串定位、打开或操作文件。
  • 标清命中位置的单位：字符索引、UTF-8 字节偏移与 UI 字形位置不可混用。归一化后若长度变化，映射回原始显示文本再着色。

5.4 syntect：读取在核心，高亮默认在客户端

  • core 的 preview 继续负责文件类型、语言提示、安全读取、预算和截断；客户端把预览文本交给高亮器，再转换成自身的文本样式。
  • 优先检查客户端已有组件是否已经支持语法高亮；确需 syntect 时声明在客户端依赖表，不为了“纯 Rust”就塞进 core。
  • 语法资源加载、解析与缓存避开逐帧渲染路径；缓存有界。多行语法按前文状态解析，不能把每行都当成独立文件。
  • 保留纯文本显示作为无法识别语言或高亮失败时的可用结果；长行和复杂输入的开销需要测量，不在 UI 线程同步处理整份文件。
  • 不把 ANSI、HTML、主题颜色或 syntect::Style 放进 core 的公共预览契约；文件内容一律当文本，不执行其中代码或把它作为活动 HTML。
  • 只有多个客户端真正需要复用语法解析时，再评估共享不带主题的语法范围；颜色和字体始终由各端决定。现在不新增高亮服务或额外 crate。

6. 实施顺序与验收

每次只引入满足当前需求的一项；以下是实施检查顺序，不是功能排期。

  1. 确认范围：对应一个已确认的搜索、筛选或预览需求；检查路线图的明确不做项。库具有某项能力，不意味着产品允许开放它。
  2. 固定语义：写清保留的行为、主动改变的行为和不支持的情况；现有实现不足的地方单独列出，不把它美化成已满足的保证。
  3. 测量基线：release 模式，记录同一批文件、相同忽略范围、相同机器和缓存条件下的首次结果、完成耗时、内存与取消延迟；不拿少扫描了一半文件当提速。
  4. 最小接入：只改相应层的依赖和内部实现，保留现有契约；真有新增生命周期需求才扩契约。不要增加运行期后端选择器或插件接口。
  5. 验证两端边界：core 用无界面测试验证业务结果；客户端用实际事件与页面/窗口验证交互，不靠直接调用处理函数证明键盘仍可用。
  6. 决定是否保留：收益成立且回归通过才采用；代价超过收益就不合入实验。记录确切依赖版本、feature、MSRV、许可证及资源许可，再同步两份文档。

7. 实施前必须拍板的问题

问题推荐起点，不是已批准决定
是否引入需求驱动，逐项评估；不在这轮核心/客户端拆分中顺手把四项接齐
模糊匹配覆盖哪里从命令面板开始；不默认改普通目录筛选和排序
搜索是否遵守项目忽略规则作为显式选项评估；不随换库改变已有搜索范围，更不改变浏览列表
是否改变内容搜索语法、编码或大小上限先保持当前语义；每项扩展单独确认和测试
是否把搜索收进统一契约多客户端确实需要统一任务生命周期时再扩；不要误认为现在已经覆盖
高亮是否共享初期留客户端；出现真实复用需求后才评估不带主题的语法数据

不纳入本参考的范围：插件系统、压缩包内搜索、全文编辑器、自动安装外部 CLI。远程协议也不会因为引入本地扫描库自动获得搜索能力；不得悄悄下载整棵远程目录来实现本地搜索。
